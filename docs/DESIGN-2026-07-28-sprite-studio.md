# 스프라이트 스튜디오 — 시각 요소 통합 편집 툴 설계

> **계획 상태:** 완료
> **상태 갱신:** 2026-08-05 — 레지스트리·편집 UI에 런타임 미사용 PNG 감사와 안전한 보관함 이동 탭까지 구현됐다.

- 작성일: 2026-07-28
- 발단: 헤드박스 에디터는 전투 화면 비율 전용. 오버월드의 스프라이트 비율·작업 위치·
  건물 효과(불빛·연기·불꽃)를 눈으로 보면서 만질 수 있는 통합 툴이 필요하다
- 범위: 데이터 레지스트리 4종 추출 + 브라우저 편집 툴 (비율 정렬대 · 작업 자세 · 건물)
- 구현: 다른 작업자 인수인계 전제
- 구현계획: `IMPLEMENTATION-2026-07-28-sprite-studio.md` — **구현자는 그 문서를 따른다**

## 1. 현재 상태 — 문제의 소재

| 문제 | 원인 | 위치 |
|---|---|---|
| 주민·행동별 크기 미묘한 불일치 | **시트마다 제각각인 `displaySize`** — 보행·지게·작업·I2V 시트가 각자 크기를 가짐 | `atlas.ts:950` `drawResidentCellRect` 등 각 draw 경로. `sizeScale` 파라미터 훅은 이미 있음 |
| 작업 위치가 어긋남 (채광꾼이 노두를 밟고 섬) | 작업 배치가 **타일 중심 기준 획일 공식** — 대상물과의 관계 없음 | `residentWorkLayout.ts` (좌우 벌리기만) |
| 효과 위치 조절 불가 | 굴뚝 연기·불꽃·작업 반짝임이 **렌더러 하드코딩 공식** | `renderer.ts:513` `drawChimneySmoke` (`bx + TILE×footprint − 4, by − 13`), `drawWorkplaceActivity` (`size×0.7, 0.68`), 밤 창불빛 (`:1577` 부근) |
| 건물별 커스텀 불가 | 효과 종류가 `workplacePresentation.ts`의 3분류(fire/craft/service)뿐, 위치·개수 지정 없음 | `workplacePresentation.ts` |

### 증명된 선례 — 헤드박스 에디터

`head_box_editor.mjs`가 이미 이 툴의 원형이다:
**브라우저 편집 → JSON 저장(`tools/game/head-boxes/`) → 코드젠(`gen:sprite-metrics`) →
게임은 생성된 TS(`tacticalSpriteMetrics.ts`)만 읽음.** 이 패턴을 오버월드로 확장한다.

## 2. 원칙

1. **에디터는 데이터를 만들고, 게임은 생성된 TS만 읽는다.** 런타임 파일 로드 없음,
   결정성·번들 불변
2. **S0(레지스트리 추출)은 동작 불변이어야 한다.** 초기 레지스트리 값 = 현재 하드코딩
   공식의 스냅샷. 추출 직후 화면이 1px도 달라지지 않는 것이 검증 기준
3. 미리보기는 **실제 게임 그리기 코드**로 그린다 — 모조 프리뷰는 실물과 어긋나면 툴을
   못 믿게 된다 (Vite 기반이라 `src/render/*`를 그대로 import 가능)

## 3. 데이터 레지스트리 3종

전부 `tools/game/sprite-studio/*.json`(편집 원본) → 코드젠 → `src/render/*.ts`(게임 소비).

### 3-1. 스프라이트 표시 비율 — `spriteDisplayMetrics`

```ts
// 키: 시트/직업/행동/성별 조합 (에셋 모듈 구조를 따라 평탄화)
// 예: "locomotion", "work.miner", "jige.hauler", "video-work.woodcutter.female"
interface SpriteDisplayMetric {
  scale: number;   // displaySize 배율 (1 = 현재)
  dy: number;      // 발끝 기준선 보정 (px)
}
```

- 적용: 각 draw 경로의 `displaySize` 계산에 `× metric.scale`, y에 `+ metric.dy` —
  기존 `sizeScale` 파라미터와 같은 자리
- 전술 전투는 기존 `tacticalSpriteMetrics`가 담당하므로 **오버월드 전용**. 중복 없음

### 3-2. 작업 자세 앵커 — `workAnchors`

```ts
// 키: 작업 문맥 — "직업@대상" (예: "miner@rockDeposit", "woodcutter@tree",
//     "farmer@field", "builder@site", "miner@mineShaft" ...)
interface WorkAnchor {
  offsetX: number;    // 대상 타일 중심 기준 스프라이트 발끝 오프셋 (px)
  offsetY: number;
  facing: 1 | -1 | 'towardTarget';  // 대상을 바라보게 할지
  toolTipX?: number;  // 도구 접점 (곡괭이 끝이 노두에 닿는 지점) — 검증 표시용
  toolTipY?: number;
}
```

- 적용: `residentWorkLayout.ts`의 벌리기 로직은 유지하되, **기준점이 타일 중심이 아니라
  앵커**가 된다. 채광꾼이 노두 옆에 비껴서고 곡괭이가 노두를 두들기는 그림
- `toolTip`은 게임 로직에 안 쓰고 에디터 안에서만 정합 확인용으로 표시

### 3-3. 건물 효과 앵커 — `buildingEffects`

```ts
// 키: 건물 타입. 값: 이미터 배열 — 추가/제거/이동 전부 데이터
interface BuildingEffectEmitter {
  kind: 'chimneySmoke' | 'fireSparks' | 'craftGlint' | 'windowGlow' | 'serviceGlow';
  x: number;          // 발자국 기준 정규화 0~1
  y: number;
  scale?: number;     // 효과 크기 배율
  when: 'working' | 'night' | 'winterHeating' | 'always';
}
```

- 적용: `drawChimneySmoke`·`drawWorkplaceActivity`·밤 창불빛이 하드코딩 좌표 대신
  이 배열을 순회. 기존 3분류(fire/craft/service)는 초기 데이터 변환의 씨앗이 되고,
  이후는 건물별로 자유 편집
- 한 건물에 이미터 여러 개 가능 (굴뚝 둘, 창 셋), 0개도 가능 (효과 제거)

### 3-4. 건물 야외 작업자 슬롯 — `buildingWorkerSlots`

장작마당의 장작꾼은 현재 `goTo(buildingGoal)`로 건물 **주변 아무 인접 칸**에 도착해
그 자리에서 일한다 (`agents.ts:1942`, `buildingInteractionGoal`이 인접 칸 전부를 목표로
줌). 그래서 매번 위치가 다르다. 건물별로 야외 작업 위치를 고정할 수 있게 한다.

```ts
// 키: 건물 타입. 값: 슬롯 배열 (작업 슬롯 수만큼 — 장작마당이면 2개)
// 등록하지 않은 건물 = 현행 유지. 밭·논은 등록하지 않는다 (농부는 지금이 자연스럽다)
interface BuildingWorkerSlot {
  tileDX: number;     // 건물 원점 기준 서는 칸 (통행 가능해야 함)
  tileDY: number;
  offsetX: number;    // 칸 안 픽셀 미세 조정 (장작 패는 그루터기 옆 등)
  offsetY: number;
  facing: 1 | -1 | 'towardBuilding';
}
```

**순간이동 없는 적용 — 두 계층으로 나눈다:**

1. **시뮬레이션 (칸 단위)**: 슬롯이 등록된 건물로 출근하는 작업자는
   `buildingInteractionGoal`이 인접 칸 전부가 아니라 **빈 슬롯 칸**을 목표로 준다.
   작업자가 실제로 그 칸까지 걸어가므로 렌더 순간이동이 없다.
   슬롯 배정은 근무자 id 순으로 결정적. 슬롯 칸이 막혀 있으면 기존 인접 칸으로 폴백
2. **렌더 (픽셀 단위)**: 근무 중일 때만 `offsetX/Y`·`facing` 적용 —
   `residentWorkStances`의 렌더 전용 오프셋 관례 그대로. 슬롯 근무자는 기존
   벌리기 로직에서 제외

이 레지스트리만 유일하게 게임 로직(`agents.ts`)을 건드린다 — §5에서 별도 단계로 분리한다.

## 4. 스튜디오 툴

### 4-1. 기반

- **Vite 페이지** `tools/game/sprite-studio/` — 실제 `src/render` 모듈을 import해
  진짜 그리기 코드로 미리보기 (기존 `resident-i2v-vite` 툴 선례 있음)
- 저장은 Vite dev 서버 플러그인(`configureServer`)의 POST 엔드포인트 —
  JSON 기록 + 코드젠 실행 (헤드박스 에디터의 저장→재생성 버튼과 동일한 UX)
- `launch.json`에 항목 추가, `npm run edit:sprites`

### 4-2. 탭 A — 비율 정렬대

- 전 주민 스프라이트(직업 × 행동 × 성별)를 **한 화면에 격자로 도열** — 게임 배율,
  발끝 기준선과 참조 눈금 표시
- 기준 실루엣(보행 시트의 표준 체형)을 반투명으로 겹쳐 이상치가 한눈에 보이게
- 항목 클릭 → scale/dy 슬라이더 + 미세 조절 버튼. 조절 즉시 정렬대에 반영
- 걷기/작업 애니메이션 재생 토글 — 정지 프레임만으로는 크기 체감이 어긋난다

### 4-5. 자산 정리

- `public/assets/*.png`를 `src/`의 코드·JSON 매니페스트 참조와 대조해 사용 중·동적 참조·미사용으로 분류한다.
- 계절 지형 텍스처와 직업별 지게 시트처럼 템플릿 문자열로 로드하는 자산은 동적 참조 규칙으로 보호한다.
- 미사용 후보는 이미지·크기·대체 자산을 나란히 확인한 뒤 선택 항목만 `tools/render/archive/`로 이동한다.
- 생성 원본과 `events/`, `ui/`, `tactical/` 등 하위 폴더는 1차 감사 범위에서 제외한다.

### 4-3. 탭 B — 작업 자세

- 작업 문맥 선택 → **모의 장면**: 실제 지형 타일 + 대상물(노두·나무·밭 등 실제
  스프라이트) + 작업 애니메이션이 도는 주민
- 주민을 드래그해 offset 조정, facing 토글, 도구 접점 십자 표시를 대상물 위에 놓고 확인
- 같은 문맥의 다인 작업 미리보기 (벌리기 로직까지 겹쳐 확인)

### 4-4. 탭 C — 건물 (효과 + 작업자 슬롯)

건물 하나를 고르면 두 레이어를 같은 화면에서 편집한다.

**효과 레이어**
- 실제 건물 스프라이트 + 상태 토글 (낮/밤 · 가동/비가동 · 겨울 난방)
- 이미터 목록: 드래그로 이동, `+`로 종류 골라 추가, `−`로 제거, scale 슬라이더
- 효과는 실제 draw 함수로 **살아 움직이는 채로** 편집 — 연기 오르는 위치를 보며 놓는다

**작업자 슬롯 레이어**
- 건물 주위 칸에 슬롯 마커를 놓고 (통행 불가 칸은 배치 거부), 칸 안에서 픽셀 미세 조정,
  facing 토글
- 미리보기: 해당 직업의 **실제 작업 애니메이션**(장작 패기 등)이 슬롯마다 재생 —
  "고정하면 이렇게 보인다"를 저장 전에 확인
- 슬롯 0개 = 현행 유지(주변 아무 데나). 슬롯 레이어를 켜는 것 자체가 "고정할지"의 선택

**그림자 레이어**
- 건물 그림자는 스프라이트 알파에서 자동 투영되지만, 건물별 노브가 있다
  (기존 `COURTYARD_SHADOW_OVERRIDES`의 승격): 마당형 모드(마당 비율·본채 접지선),
  그림자 없음, 건물별 길이 배율
- 태양 슬라이더(아침~저녁)·계절 셀렉터로 실제 투영 코드의 그림자를 훑으며 조절
- 나무·주민 그림자와 태양 물리는 전역 시스템이라 편집 대상이 아니다

## 5. 구현 순서

| 단계 | 내용 | 검증 |
|---|---|---|
| S0 | 레지스트리 추출(비율·작업 앵커·효과) — 현재 값 스냅샷, 렌더러 소비 전환 | **화면 동작 불변** (전환 전후 스크린샷 비교) |
| S1 | 스튜디오 셸 — Vite 페이지 + 저장/코드젠 서버 + launch.json/npm 스크립트 | 열리고 저장됨 |
| S2 | 탭 A 비율 정렬대 | 조절→저장→게임 반영 |
| S3 | 탭 B 작업 자세 | 채광꾼-노두 정합 |
| S4 | 탭 C 건물 — 효과 레이어 | 이미터 추가/제거/이동 |
| S4b | **작업자 슬롯** — `buildingWorkerSlots` 레지스트리 + `buildingInteractionGoal` 슬롯 목표 + 렌더 오프셋 + 탭 C 슬롯 레이어 | 장작마당 2인 고정 자세, 슬롯 막힘 폴백 |
| S5 | (선택) 헤드박스 에디터를 탭 D로 통합 | 기존 파일 형식 유지 |

S0(렌더 데이터화)와 S4b(작업자 슬롯)만 게임 코드를 건드린다. S0는 동작 불변 리팩터,
**S4b는 유일하게 동작이 바뀌는 단계**(작업자의 실제 목표 칸이 달라짐)라 따로 뗐다 —
장작마당 하나로 먼저 검증하고 다른 건물로 넓힌다. S1~S4는 툴 코드라 게임에 영향이 없다.

## 6. 열어 둔 판단

- 비율의 "기준"을 무엇으로 삼나 — 보행 시트 표준 체형을 1.0으로 두는 안이 유력하나,
  정렬대에서 실물을 보고 정하는 게 맞다 (그러라고 만드는 툴이다)
- 슬롯 칸이 다른 주민에게 점유된 순간의 처리 — 폴백(아무 인접 칸)이면 충분한지,
  잠깐 기다리게 할지. 1차는 폴백
- 작업 문맥 키의 입도 — 직업@대상이면 충분한가, 도구 종류까지 필요한가
- 효과 이미터의 `when` 조합 (겨울+밤 등) — 1차는 단일 조건, 필요 시 배열로
- 스튜디오에서 편집 중 실게임 핫리로드 — 코드젠이 TS를 다시 쓰므로 Vite HMR이
  자동으로 게임 dev 서버에 반영된다. 두 서버를 같이 띄우면 실게임 확인이 공짜인지 검증
