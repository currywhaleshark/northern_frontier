## 0. 방향성 검토 결론

**개편안의 큰 방향을 승인한다.** 현행 튜토리얼은 2026-07 중순 이전 시스템(밭·장작·집·사냥·목책·세공)만 다루며, 이후 들어온 물·부패·의료·재해·외교 인물·전술전·가축·광산을 전혀 안내하지 않는다. 개편안의 3층 구조는 현행 코드 구조에 자연스럽게 얹힌다.

| 층 | 개편안 | 현행 코드의 수용 지점 |
|---|---|---|
| 필수 길잡이 (첫 겨울) | 8스텝 → 11스텝 재구성 | `TUTORIAL_STEPS` 술어 스텝 — 구조 그대로, 내용 교체 |
| 통제 사건 (scripted incident) | 병자 1명·혹한 경고 | 스텝 정의에 일일 훅 추가 (신규, §4) |
| 선택형 길잡이 (완료 후·일반 게임 공통) | 시스템 초회 1회 안내 | **신규 상태 필요** — scenario와 분리해야 함 (§5, 핵심 수정점) |

개편안의 전제 대부분이 코드와 일치함을 확인했다(§1). 어긋나는 전제와 조정이 필요한 지점은 §2에 정리했다. 가장 중요한 수정 제안은 두 가지다:

1. **파종과 집·장작은 병행 구조로 푼다** (2026-07-31 사용자 확정) — 경작지 조성은 농부, 건물 공사는 건축가 담당이라 노동력이 겹치지 않는다. 파종 스텝은 "배치"에서 완료되고 실제 파종은 집·장작 스텝과 병행 진행 — 봄 파종 시한 리스크도 함께 해소된다. (§2-가)
2. **완료 후 선택형 길잡이는 `state.scenario`가 아니라 별도 `state.guides`로 만든다** — 랜덤 사건 잠금이 `scenarioActive()`에 걸려 있어, scenario를 유지한 채 안내만 켜 두면 랜덤 사건이 영영 열리지 않는다. (§5)

## 2. 개편안 대조 검토 — 조정이 필요한 지점

### 가. 파종과 집·장작의 병행 구조 (2026-07-31 사용자 방향 확정)

개편안은 "사람이 얼어 죽는다가 더 직관적"이라는 이유로 집·장작(2장)을 파종(3장)보다 앞에 뒀고, 초안 검토에서는 봄 파종 시한 때문에 순서 교체를 권고했다. 이후 사용자가 핵심 사실을 짚었다: **경작지 조성은 이제 건축가가 아니라 농부가 맡는다.** 코드로 확인 — `agents.ts:1581`·`simulation.ts:500`에서 `isPlotBuildingType`(밭·논)은 `farmer`, 그 외 건물은 `builder`가 공사 담당. 즉 밭 갈이와 집·장작마당 건설은 노동력이 겹치지 않아 **병행이 가능하다.**

확정 구조 — 순차 스텝 엔진을 유지하면서 병행을 살린다:

- **2단계 「봄 파종」 완료 조건을 "밭 4칸 이상 배치"로 낮춘다.** 플레이어의 행동(드래그 배치·작물 선택)은 몇 초면 끝나고, 갈이·파종은 농부가 배경에서 진행한다. 배치 즉시 다음 스텝으로 넘어가므로 파종 시한 리스크가 사라진다.
- **3단계 「집과 장작」 isDone에 `totalSownArea ≥ 4`를 병행 조건으로 포함한다.** 건축가가 집·장작마당을 짓는 동안 농부의 파종이 함께 끝나는 그림 — "직업마다 제 일을 한다"는 1단계의 가르침이 실제로 눈앞에서 재현된다. 파종이 정체되면(농부 0명 등) 코치가 농부 배정을 가리킨다.
- 집·장작의 "얼어 죽는다" 서사는 3단계 본문에서 살린다.

### 나. 정착지 이름과 개칭 청원 (2026-07-31 사용자 방향 확정)

프롤로그의 이름 서사는 **시작 시 입력이 아니라 개칭 청원으로 푼다.**

- 0단계는 개편안 원문 목표 그대로 **이름 '확인'** — 현행 고정 이름('길잡이촌')을 유지하고, 본문("오늘부터 이 이름은 조정의 문서와 주민들의 기억에 남습니다")으로 서사만 심는다. `MainMenu`·`tutorialStart` 변경 없음, 회귀 테스트도 그대로.
- **개칭 청원은 첫 겨울을 버틴 뒤에 안내한다** — `settlementName.ts`에 이미 구현된 파발 왕복 행정 절차(북병사 명의 허가, 연대기 기록)를 선택형 길잡이 `rename` 모듈로 소개한다(§5 트리거 표). "이름을 조정의 문서에 올리는 일"이라는 프롤로그 서사가 7단계(조정의 몫)를 거쳐 첫 겨울 이후 실제 행동으로 완결되는 흐름이다.
- 트리거: 튜토리얼 완료 직후. 일반 게임은 첫 겨울을 넘긴 봄 첫날.

### 다. 혹한 scripted incident의 구현 방식

날씨는 결정적 연간 기후(`climate.ts`)가 생성하므로, 튜토리얼이 임의로 "혹한 하루"를 삽입하면 결정론·기후 정합이 깨진다. 두 안:

- **A안 (권고): 기후를 건드리지 않는다.** 겨울 스텝 진입 후 n일째에 "장작 소모 급증" 경고 이벤트 + 해당일 장작 소모 소폭 배율(예: ×1.3)만 스텝 훅으로 적용. 저장 필드 불필요, 기후 시스템 무손상.
- B안: `climate`에 튜토리얼 전용 오버라이드 훅 추가. 실제 혹한 연출은 정확하지만 침습적.

→ 결정 항목 3

### 라. 첫 병자 scripted incident

역병 시스템(`plagueCase`/`epidemic`)을 쓰지 않고, 스텝 `onStart`에서 **건강한 성인 1명에게 `sick` 부여 + 경고 로그**로 충분하다. 기존 의료 파이프라인(의원 진료·약초 소모·자연 회복)이 그대로 처리한다. 완료 조건은 "해당 병자의 회복"(관찰 학습)을 권고 — 의원·격리는 본문 소개만. → 결정 항목 4

### 마. 코치 힌트가 개편안에 누락됨

`TutorialCoach`는 스텝별 `data-tut` 앵커 경로(`STEP_HINTS`)로 "다음에 누를 곳"을 가리킨다. 개편안의 UI 3층(목표 칩·길잡이 카드·초회 팝업) 중 "길잡이 카드"의 역할을 사실상 이 코치가 이미 하고 있다. **신규 카드 컴포넌트를 만들기보다 코치를 확장**하고, 신규 스텝마다 힌트 경로와 앵커를 함께 설계해야 한다(§6). 앵커가 없는 대상: 미니맵, 수맥 탭, 연대기 버튼, 조정 창의 북병사 영역, 파수꾼 직업 상세.

### 바. 신규 스텝의 맵 불변식

물 스텝(우물/자연 급수)이 들어가면 `TUTORIAL_SEED`(20260718) 맵에 마을 근처 수맥 또는 강 급수 가능 지점이 보장되어야 한다. `ensureTutorialInvariants()`에 수맥 불변식을 추가하고, 시드가 조건을 못 채우면 재선정한다. 회귀 테스트가 이 불변식을 함께 검증한다.

### 사. 개편안 중 이미 구현되어 있는 것

- 구버전 튜토리얼 저장 해제 (`saveLoad.ts`) — 버전 상수 3으로 올리는 것 외 작업 없음
- "중심지 → 연대기" 진입점, 수맥 레이어의 우물 배치 중 자동 표시
- 세공 스텝의 `announceCourtTribute` onStart 훅 (유지)

| # | id | 제목 | 목표 (칩) | isDone 술어 초안 | 신규 요소 |

| 5 | `hunting` | 사냥과 부패 | 사냥꾼 2명 + 고기 목표 확보 | 현행 유지 | 부패 경고 본문 강화, 보존 시설 예고 |

| 7 | `tribute` | 조정의 몫 | 조정 창에서 북병사 확인 + 세공고 비축 | 현행 ∧ `courtWindowOpened` | 북병사·명성·의심 본문(수치는 설명만 — 게이트로 변동 없음) |
| 8 | `defense` | 방어의 기초 | 목책 + 수비병 1명 + 파수꾼 1명 | 현행 ∧ watchman≥1 | 수비병/파수꾼 구분 본문, 봉수대·망루는 예고만 |
| 9 | `stocktake` | 겨울 점검 | 겨울 점검 패널에서 식량·장작 기준 충족 | `checklistOpened` ∧ 식량 n일분 ∧ 장작 n일분 | 겨울 점검 패널 신규(§6), 일분 계산 신규 |

- 목표 수치(`firewoodGoal` 등)는 현행처럼 `createTutorialScenarioState` 플래그로 주입한다. 겨울 점검 기준(n일분)도 같은 방식.
- UI 훅 플래그(`minimapClicked`, `jobPanelOpened`, `aquiferToggled`, `courtWindowOpened`, `checklistOpened`)는 현행 `markScenarioFlag` 경로를 그대로 쓴다 — 각 컴포넌트에 한 줄 호출 추가.
- 스텝 수 11개는 현행 모달-스텝 구조 그대로 수용 가능. 모달 피로는 본문 길이 절제와 코치 이관으로 줄인다(§6).

## 4. 통제 사건 (scripted incidents)

별도 전역 시스템을 만들지 않는다. `ScenarioStepDefinition`에 선택적 일일 훅을 추가하는 최소 설계:

```ts
interface ScenarioStepDefinition {
  // …현행…
  onStart?: (state: GameState) => void;          // 현행 유지
  onDay?: (state: GameState, rng: Rng) => void;  // 신규 — 스텝 진행 중 매일 endOfDay에서 호출
}
```

- 호출 지점: `dailyScenarioTick` 안, `isDone` 판정 전. 게이트(`scenarioSuppressesRandomEvents`)와 무관하게 동작하므로 개편안의 "잠금은 유지하되 통제 사건은 허용" 요구를 그대로 충족한다.
- 사건 목록 (첫 판 범위):
  - **첫 병자** (6단계 onStart): 성인 1명 `sick` + 경고 로그 (§2-라)
  - **장작 소모 급증** (10단계 onDay, 겨울 n일째 1회): 경고 이벤트 + 당일 소모 배율 (§2-다 A안 기준)
- 화재·습격은 개편안대로 첫 튜토리얼에서 제외 — 선택형 길잡이(§5)로 넘긴다.
- 진행 위치만 저장하는 현행 원칙 유지 — 훅은 코드에 있으므로 저장 마이그레이션 불필요. 단 "혹한 경고를 이미 띄웠는지"는 `scenario.flags`에 기록한다.

## 5. 선택형 길잡이 (초회 도움말) — 튜토리얼 완료 후·일반 게임 공통

**scenario와 분리된 신규 상태가 필수다.** `scenarioSuppressesRandomEvents()`가 `scenarioActive()`를 반환하므로, scenario를 유지한 채 안내를 계속하면 랜덤 사건이 열리지 않는다. 완료 시 scenario는 현행처럼 `null`로 끝내고:

```ts
// types.ts — GameState에 추가
guides?: {
  enabled: boolean;              // 완료 모달·설정에서 토글
  seen: Record<string, number>;  // 모듈 id → 본 날짜 (1회성 보장)
};
```

- 완료 모달 선택지를 개편안대로 2개로: **[계속해서 안내받는다]** / **[이제 스스로 운영한다]** → `guides.enabled` 설정. 완료 문구도 개편안 문안("첫 겨울은 끝났지만 북방은 이제부터입니다…")으로 교체.
- **일반 게임에도 확대한다 (2026-07-31 사용자 확정)** — 모든 새 게임은 `guides.enabled = true` 기본. 튜토리얼을 거치지 않은 초보자도 시스템 첫 등장 시 안내를 받는다.
- `SettingsDialog`에 상시 토글 추가 (사용자 확정 — 옵션에서 켜고 끌 수 있게). 구버전 저장은 `guides` 부재 시 `{ enabled: false, seen: {} }` 보정 — 이미 시스템을 아는 진행 중 마을에 뒤늦은 안내가 쏟아지지 않게 한다. 저장 스키마 버전 상승 1회.
