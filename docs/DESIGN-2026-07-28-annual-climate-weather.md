# 연간 기후와 실제 날씨 연결 — 설계

- 작성일: 2026-07-28
- 발단: 측우기가 공개하는 연간 재해 확률을 실제 비·눈·한파의 빈도와 연결한다
- 범위: `AnnualClimate` 생성 + 계절 날씨표 생성 + 기존 일일 날씨 추첨 교체
- 후속: `DESIGN-2026-07-28-court-grants.md`의 측우기·재해 확률

## 1. 현재 구조와 문제

현재 `weather.ts`의 `rollWeather(day, rng)`는 계절별 고정 가중치인 `CONFIG.weather.table[season]`에서
매일 날씨를 독립 추첨한다.

```ts
export function rollWeather(day: number, rng: () => number): WeatherId {
  const season = getSeason(day);
  return pickWeighted(rng, CONFIG.weather.table[season]);
}
```

이 방식에서는 모든 해의 기후가 통계적으로 같고, 이른 서리 같은 재해 확률과 실제 날씨 사이에도
연결이 없다. 연간 건조도를 추가해 일일 가중치만 조절할 수도 있지만 한 계절이 12일뿐이라
운에 따라 **건조한 해가 다습한 해보다 비가 더 많이 오는 역전**이 자주 생길 수 있다.

따라서 연간 기후는 일일 주사위의 약한 보정이 아니라, 그해 각 계절에 실제로 나타날
날씨 일수와 배열을 결정하는 원본으로 사용한다.

## 2. 목표

- 같은 세계·같은 연도에는 항상 같은 기후와 날씨가 나온다.
- 건조한 해에는 실제 비와 눈이 오는 날이 줄어든다.
- 추운 해에는 서리·폭설·눈보라·혹한이 늘고 비는 눈 쪽으로 이동한다.
- 폭풍성이 높은 해에는 평범한 강수보다 폭설·눈보라 같은 극단 날씨 비중이 높아진다.
- 실제 일일 날씨가 농사·작업·난방에 미치는 기존 효과가 그대로 기후 체감이 된다.
- 저장 상태를 크게 늘리지 않고 구세이브를 그대로 읽을 수 있어야 한다.
- 측우기 UI와 재해 판정은 이 기후값을 공유하되, 기후 시스템 자체는 하사품과 독립적으로 동작한다.

## 3. 연간 기후

연간 기후는 세계 시드와 연차에서 결정적으로 계산한다.

```ts
export interface AnnualClimate {
  temperatureAnomaly: number;   // -1 한랭 ~ +1 온난
  precipitationAnomaly: number; // -1 건조 ~ +1 다습
  storminess: number;           // -1 잔잔 ~ +1 거침
}

export function annualClimate(seed: number, year: number): AnnualClimate;
```

세 축은 서로 다른 salt로 뽑는다. 새 축을 추가해도 기존 온도·강수값이 바뀌지 않게 한다.
각 값은 처음에는 균등분포가 아니라 중앙값 근처가 자주 나오고 극단값은 드문 삼각분포로 만든다.

```ts
anomaly = rng() - rng(); // -1~+1, 0 부근이 흔함
```

연간 기후는 저장하지 않고 `seed + year`에서 다시 계산한다. 따라서 구세이브 필드 추가가 필요 없고
저장/불러오기로 기후를 바꿀 수 없다.

### 플레이어용 표현

기후값 자체는 소수로 노출하지 않는다.

| 값 | 표현 예시 |
|---|---|
| 강수 −0.6 이하 | 매우 건조 |
| 강수 −0.2 이하 | 건조 |
| 강수 −0.2~+0.2 | 예년과 비슷 |
| 강수 +0.2 이상 | 습윤 |
| 강수 +0.6 이상 | 매우 습윤 |

온도는 `매우 추움 / 추움 / 평년 / 온화함 / 매우 온화함`, 폭풍성은
`잔잔함 / 평년 / 궂은 날이 잦음`으로 표현한다.

측우기가 없더라도 플레이어는 실제 날씨를 통해 그해 기후를 체감한다. 측우기가 있으면
기물함 또는 날씨 상세 UI에 **금년 관측: 건조 · 추움 · 궂은 날이 잦음**처럼 명시한다.

## 4. 기후를 계절별 날씨 가중치로 변환

기존 `CONFIG.weather.table`은 평년의 계절별 기본 가중치로 유지한다. 기후는 이 값을 직접 덮어쓰지 않고
날씨 종류별 배율을 적용한다. 기본 가중치가 0인 계절에는 기후가 변해도 그 날씨가 새로 생기지 않는다.

```ts
precipMult = clamp(1 + 0.45 * precipitationAnomaly, 0.55, 1.45);
coldMult = clamp(1 - 0.40 * temperatureAnomaly, 0.60, 1.40);
warmMult = clamp(1 + 0.25 * temperatureAnomaly, 0.75, 1.25);
stormMult = clamp(1 + 0.40 * storminess, 0.60, 1.40);
```

날씨는 먼저 **강수일**과 **비강수일**로 나눈다.

- 강수일: `rain`, `heavySnow`, `blizzard`
- 비강수일: `clear`, `frost`, `coldSnap`
- `thawFlood`: 직전 겨울 적설에서 따로 산출하며 비강수일 일부를 대체

계절 기본표에서 강수 계열의 합을 구한 뒤 `precipMult`로 총 강수일 비중을 조정한다.
온도와 폭풍성은 총 강수일 수를 다시 늘리지 않고, 정해진 강수일 안에서 비·폭설·눈보라의 몫만 바꾼다.

| 날씨 | 같은 그룹 안에서의 상대 가중치 |
|---|---|
| `clear` | 기본값 |
| `rain` | `warmMult` |
| `frost` | `coldMult` |
| `heavySnow` | `coldMult` |
| `blizzard` | `coldMult × stormMult` |
| `coldSnap` | `coldMult × stormMult` |
| `thawFlood` | 강수량과 직전 겨울 적설일을 사용하는 별도 계산 |

건조도는 비뿐 아니라 눈·눈보라도 함께 줄인다. 온도는 강수의 양보다 형태를 바꾸어,
추운 해에는 비보다 눈 계열이 상대적으로 늘어난다.

### 해빙기 홍수

해빙기 홍수는 현재 봄 고정 가중치지만, 다음 두 값에 연결한다.

- 직전 겨울의 `heavySnow + blizzard` 예정 일수
- 현재 봄의 `temperatureAnomaly`

눈이 많이 쌓였고 봄이 따뜻할수록 가중치가 높아진다. 직전 겨울 날씨표도 결정적으로 재생성할 수 있어
별도 적설량 상태는 필요 없다. 1년차 봄은 직전 겨울이 없으므로 평년 적설값을 사용한다.

## 5. 12일짜리 계절 날씨표

보정된 가중치에서 매일 독립 추첨하지 않는다. 계절이 시작될 때와 같은 결과를 내는
`seasonWeatherSchedule(seed, year, season)`을 만들어 12일치 날씨를 결정한다.

### 5-1. 일수 배분

1. 평년 강수 계열 합계에 `precipMult`를 적용해 **총 강수일 수의 기대값**을 먼저 구한다.
2. 기대값을 **확률적 반올림 + 계절 변덕**으로 실제 일수로 바꾼다 (아래 5-1-1).
3. 강수일 안에서 `rain / heavySnow / blizzard`의 기대 일수를 구한다.
4. 비강수일 안에서 `clear / frost / coldSnap`의 기대 일수를 구한다.
5. 각 그룹 안에서는 먼저 내림한 뒤 소수점 잔여가 큰 순서로 남은 날짜를 배정한다.
6. 잔여가 같으면 계절 전용 RNG로 순서를 정한다.
7. 봄의 `thawFlood` 일수는 계산된 만큼 비강수일 중 `clear`를 우선 대체한다.

이 방식이면 모든 날씨 일수의 합이 정확히 12가 된다.

#### 5-1-1. 계절 변덕 — 같은 기후라도 해마다 하루이틀 다르다

기대값을 그냥 `round()`하면 한 계절이 12일뿐이라 문제가 생긴다. 하루가 계절의 8.3%이므로
**중간 anomaly 구간(−0.2~+0.2)이 전부 같은 일수로 뭉개진다.** "예년과 비슷"한 해들이
전부 똑같은 날씨 구성을 갖게 되어, 기후가 라벨로만 존재하고 체감되지 않는다.

두 단계로 편차를 준다.

```ts
// 1) 확률적 반올림 — 소수부를 확률로 쓴다
//    기대 3.6일 → 60% 확률로 4일, 40% 확률로 3일
base = Math.floor(expected) + (seasonRng() < expected % 1 ? 1 : 0);

// 2) 계절 변덕 — 같은 기후여도 해마다 흔들린다
jitter = weightedPick(seasonRng, { '-1': 0.15, '0': 0.70, '+1': 0.15 });

precipDays = clamp(base + jitter, 0, 12 - thawFloodDays);
nonPrecipDays = 12 - precipDays - thawFloodDays;
```

두 단계 모두 **기대값을 바꾸지 않는다.** 확률적 반올림은 정의상 기대값이 보존되고,
계절 변덕은 좌우 대칭이라 평균이 0이다. 그래서 건조한 해가 평균적으로 비가 적다는 성질은
그대로 유지되면서, 실제 일수는 대체로 ±1일, 가끔 ±2일까지 흔들린다.

`seasonRng`는 `seed + year + season`에서 파생하므로 결정성도 유지된다.

> **대가**: 이 편차 때문에 **개별 연도의 단조성은 깨진다.** 건조한 해가 습윤한 해보다
> 우연히 비가 하루 더 올 수 있다. §1에서 "역전이 자주 생긴다"고 지적한 바로 그 현상이지만,
> 폭이 ±1~2일로 묶여 있어 **"자주 크게 역전"이 아니라 "가끔 살짝 역전"** 이 된다.
> 12일 계절에서 기후를 라벨이 아니라 체감으로 만들려면 이 정도 편차는 필요하다.
>
> 대신 **§8의 단조성 검증을 개별 연도가 아니라 표본 평균으로 바꾼다.**

### 5-2. 연속 구간 배치

날씨가 매일 맑음·폭설·맑음·폭설처럼 튀지 않도록 같은 날씨를 1~3일짜리 구간으로 나눈 뒤
구간 단위로 결정적으로 섞는다.

- `clear`, `rain`, `frost`: 최대 3일 연속
- `heavySnow`, `coldSnap`: 최대 2일 연속
- `blizzard`, `thawFlood`: 기본 1일, 극단적인 해에만 최대 2일

인접한 같은 날씨 구간은 가능하면 합치고, 같은 극단 날씨가 상한을 넘으면 맑음·서리 구간과 교환한다.
정확한 구간 배열은 체감 조정 대상이지만, 계절별 총일수는 바꾸지 않는다.

### 5-3. 실제 날씨 조회

```ts
export function weatherForDay(seed: number, day: number): WeatherId {
  const year = getYear(day);
  const season = getSeason(day);
  const index = getDayOfSeason(day) - 1;
  return seasonWeatherSchedule(seed, year, season)[index];
}
```

새 게임의 첫날과 매일 자정 모두 `rollWeather` 대신 `weatherForDay`를 사용한다.
성능상 필요하면 `year + season`을 키로 12개 배열을 메모하되 저장 데이터에는 넣지 않는다.

## 6. 기존 게임 효과와의 연결

첫 단계에서는 기후에 별도의 생산량 배율을 또 붙이지 않는다. 실제 날씨가 이미 다음 효과를 낸다.

- 비: 작물 성장 +20%, 일부 건조 작업 중단
- 폭설·눈보라: 이동·실외작업 저하와 대피
- 서리: 작물 성장 저하
- 혹한·눈보라: 난방 소비와 체온 손실 증가
- 해빙기 홍수: 강 통행과 일부 작업 저하

따라서 건조한 해는 비 성장 보너스가 줄고, 추운 해는 난방과 작업 손실이 늘어난다.
여기에 연간 생산량 페널티를 다시 곱하면 같은 기후를 이중으로 계산하므로 우선 도입하지 않는다.

이후 재해 시스템은 같은 `AnnualClimate`를 사용한다.

- 이른 서리 발생 가중치와 서리가 걷힐 확률 ← `temperatureAnomaly`
- 가뭄 발생 가중치와 비가 올 확률 ← `precipitationAnomaly`
- 황충 발생 가중치 ← 온도·강수 조합 + 재해 전용 연차 변동

## 7. 구현 순서

| 단계 | 내용 | 검증 |
|---|---|---|
| W1 | `annualClimate(seed, year)` + 기후 표현 라벨 | 같은 시드·연차 결정성, 축별 독립 salt |
| W2 | 기후 보정 계절 가중치 + 12일 일수 배분 | 합계 12, 음수·NaN 없음, 건조/습윤 단조성 |
| W3 | 연속 구간 배치 + `weatherForDay` | 연속 상한, 같은 계절 재생성 일치 |
| W4 | `simulation.ts`의 일일 독립 추첨 교체 | 새 게임·구세이브 진행, 날씨 로그 |
| W5 | 해빙기 홍수에 직전 겨울 적설일 연결 | 1년차 기본값, 다설·온난 봄 가중치 |
| W6 | 측우기 관측 UI용 기후 라벨 제공 | 보유 여부별 표시 |

W1~W4를 완료한 뒤 조정 하사품 계획의 재해 확률·측우기 단계로 넘어간다.

## 8. 필요한 집중 테스트

- 같은 `seed/year/season`이 언제나 같은 12일 배열을 만든다.
- 모든 계절 배열의 길이가 정확히 12이며 해당 계절에서 허용된 날씨만 포함한다.
- **표본 평균**으로: 동일 온도·폭풍성에서 강수 anomaly가 낮아질수록
  `rain + heavySnow + blizzard`의 **평균** 일수가 증가하지 않는다.
- **표본 평균**으로: 동일 강수에서 온도가 낮아질수록 눈·서리·혹한의 평균 일수가 감소하지 않는다.
- 계절 변덕의 폭이 기대값 대비 **±2일을 넘지 않는다** (개별 연도 상한).
- 극단 날씨의 연속 상한이 지켜진다.
- 여러 시드 표본에서 평년 기후의 평균 일수가 기존 `CONFIG.weather.table`과 크게 어긋나지 않는다.
- 구세이브를 불러온 당일 날씨는 유지하고, 다음 날부터 결정적 날씨표를 따른다.

단조성은 개별 연도가 아니라 표본 평균으로 검증한다 (§5-1-1). 개별 연도 단조성을 요구하면
계절 변덕을 넣을 수 없고, 그러면 12일 계절에서 중간 기후가 전부 같은 일수로 뭉개진다.
대신 **편차 폭 상한**을 별도로 검증해 역전이 커지지 않도록 묶는다.

전체 게임 테스트를 반복하기보다 `annualClimate`, 계절 일수 배분, 배열 생성 단위 테스트와
짧은 계절 진행 테스트만 우선 실행한다.

## 9. 열어 둔 판단

- 계절 변덕 폭(`±1: 15%씩`)이 적절한지 — 너무 크면 기후 라벨과 체감이 어긋나고,
  너무 작으면 중간 기후가 다시 뭉개진다
- 12일 배분에서 0.5일 미만의 희귀 날씨가 너무 자주 0일이 되는지
  (확률적 반올림을 넣었으므로 이제 "가끔은 나온다"로 바뀐다)
