# 정기거래 계약 — 설계

> **계획 상태:** 완료
> **상태 갱신:** 2026-07-29 — 계약 체결·연간 실행·갱신·계약고와 관련 UI까지 구현됐다.

- 작성일: 2026-07-28
- 발단: 소금 같은 교역 의존 품목을 매번 손으로 거래하는 피로. 조기 실장 목표
- 범위: 세력·상단과의 연 단위 정기거래 계약 — 체결·자동 실행·갱신·파기
- 원칙: **새 시스템 최소화** — 기존 협상·교역량·우호도·세공 캐던스에 전부 얹는다

## 1. 재사용하는 부품

| 부품 | 위치 | 계약에서의 역할 |
|---|---|---|
| 협상 (`negotiateTrade` → accepted) | `events.ts` | **체결 = 성사된 협상의 조건을 그대로 연 단위로 잠근다** |
| 우호도 마진 (`relationMargin`: 75+→1.0 / 60+→1.1 / 45+→1.25 / 미만→1.5) | `tradeValues.ts:13` | 체결 시점 마진이 계약 기간 내내 고정 |
| 계절 교역량 (`factionTradeCapacitySummary` / `useFactionTradeCapacity`) | `tradeValues.ts` | 계약 물량이 실행 계절의 교역량을 소모 |
| 연간 캐던스 (봄 공지→겨울 수거) | `courtTribute.ts` | 같은 "매일 검사 + 특정 계절 첫날 실행" 패턴 |
| 우호도 변화 (`changeRelation`, `CONFIG.relations.tradeAccept`) | `relations.ts` | 이행 시 우호도 소폭 상승, 불이행 시 하락 |
| 은 거래 | 만상·송상이 이미 `silver` 수출입 | 상단 계약 = give 또는 get이 은인 계약. **별도 분기 불필요** |

여진 씨족(오도리·니마차·올량합)은 물물교환, 상단(만상·송상)은 은 거래 —
**기존 세력 정의가 이미 그렇게 되어 있으므로 계약 모델은 하나면 된다.**
give/get에 은이 들어가면 상단 계약이 되는 것뿐이다.

## 2. 계약 모델

```ts
// types.ts
export interface TradeContract {
  factionName: string;
  give: ResourceId; giveAmt: number;   // 매년 내주는 것
  get: ResourceId;  getAmt: number;    // 매년 받는 것
  executeSeason: Season;               // 체결한 계절 — 매년 이 계절 첫날 실행
  signedYear: number;
  durationYears: number;
  yearsExecuted: number;
  missedStreak: number;                // 연속 불이행 (2회면 파기)
}

// GameState — 세이브 +1, 구세이브는 빈 배열
tradeContracts: TradeContract[];
```

- 교환비는 체결 시점에 확정되어 만료까지 불변 — 계약의 의미가 이것이다
- 실행 계절은 체결한 계절. 계절별 교역량 배율(겨울 소금이 싼 것 등)이 자동으로
  계약 조건에 반영된다 — 언제 체결하느냐가 곧 전략이다

## 3. 체결 — 협상 성사 화면에 버튼 하나

새 협상 UI를 만들지 않는다. `negotiateTrade`가 `accepted`에 도달한 화면에
**"이 조건으로 정기 계약"** 버튼을 추가한다.

- 조건: 우호도 45 이상 (마진 최하 구간에서는 계약 불가 — "낯선 상대와 연 계약은 없다")
- 버튼을 누르면 그 거래는 **1회 실행 + 계약 등록**을 함께 한다 (첫 해 이행분)
- 같은 세력과의 계약 수 상한: 2건 (품목별 1건 — 같은 get 품목 중복 불가)

### 우호도가 정하는 것

| 체결 시 우호도 | 기간 | 교환가치 |
|---|---|---|
| 45 이상 | **2~3년** | `relationMargin` 1.25 그대로 |
| 60 이상 | **4~5년** | 마진 1.1 + 계약 할인 |
| 75 이상 | **6~7년** | 마진 1.0 + 계약 할인 |

- 계약 할인: 스팟 거래보다 소폭 유리한 배율 (초기값 0.95 — "큰 손과 오래 가는 값").
  스팟 협상을 완전히 대체하지 않도록 폭은 작게 유지
- 기간의 2~3 / 4~5 / 6~7 폭은 체결 시 결정적 rng (시드+연차) — 수치는 `CONFIG.trade.contract`

## 4. 물량 — 계절 교역량과의 연동

- 계약 1건의 `getAmt` 상한 = **체결 시점 그 계절 교역량(`total`)의 50%**
  — 계약이 수동 교역을 다 밀어내지 않게
- 매년 실행 시 `useFactionTradeCapacity`로 그해 교역량을 실제 소모한다
- 실행 연도에 교역량이 줄어 있으면(등급 하락은 없지만 부두 소실 등) **들어가는 만큼만
  부분 이행** — 비례 축소하고 로그로 알린다. 불이행으로 치지 않는다

## 5. 계약고 — 장터에서 미리 채워 둔다

세공고(`tributeReserve.ts`)와 같은 구조를 계약에도 둔다. 교역이 이미 장터·부두를
요구하므로 (`canRequestTrade` — `events.ts:128`) **계약고 UI는 장터(부두) 패널**에 얹는다.

```ts
// GameState — 세공고와 동일 패턴
tradeContractReserve: Partial<Record<ResourceId, number>>;
```

- `setTributeReserve`와 같은 이동 함수 — 일반 재고 ↔ 계약고. 넣어 둔 물자는
  **일반 소비(취사·난방 등)에서 격리**된다. 소금·곡물을 계약 몫으로 지켜 두는 것이 핵심 가치
- 품목별 풀 방식 — 계약별 칸막이는 두지 않는다 (두 계약이 같은 품목을 내줄 때도
  풀 하나로 충분하고, 칸막이는 관리만 늘린다)
- 채움 상한 = 활성 계약들의 다음 1회분 `giveAmt` 합
- 계약이 전부 만료·파기되면 잔여분은 일반 재고로 자동 반환 (`releaseTributeReserve` 패턴)

## 6. 연간 실행 — 세공 캐던스 그대로

`maybeCollectTribute`와 같은 매일 검사 패턴 (`simulation.ts` 일일 처리에 한 줄):

```
실행 계절 첫날, 그해 미이행 계약이 있으면:
  계약고 → 부족분은 일반 재고 순으로 giveAmt를 채울 수 있는가?
    → 있다: 자동 실행. 자원 이동 + 교역량 소모 + 우호도 소폭 상승 + 로그
      "오도리 씨족과의 정기거래: 도구 3을 내주고 곡물 16을 받았습니다. (3/5년차)"
    → 없다: 모달 없이 3일 유예 — 유예 내 갖춰지면 실행
      유예가 지나면 불이행: 우호도 하락(위약) + missedStreak++
      missedStreak 2회 → 계약 파기, 로그로 알림
```

- **평시에는 모달이 뜨지 않는다.** 피로를 줄이는 것이 목적이므로 정상 이행은 로그 한 줄이다
- 세력이 적대 전환(습격 등)하면 계약은 자동 정지, 우호도 회복 시 재개 여부는 열어 둔 판단
- 플레이어 중도 해지: 세력 패널에서 가능, 위약으로 우호도 하락

## 7. 만료와 갱신

- 만료 계절에 실행 대신 **갱신 제안 모달** (이때만 모달) —
  현재 우호도 기준으로 새 조건(기간·마진) 재계산 제시
- `갱신` / `조건 변경 협상` (새 협상창) / `종료` 세 선택
- 갱신은 우호도가 올라 있으면 더 긴 기간·나은 마진 — 관계를 키운 보상이 자연스럽게 온다

## 8. UI

| 위치 | 내용 |
|---|---|
| TradeDialog (협상 성사 화면) | "이 조건으로 정기 계약" 버튼 + 조건 요약 (기간·연 1회·실행 계절) |
| **상단바** | **간략 칩 하나** — 아래 참조 |
| 장터(부두) 패널 | **계약고** — 품목별 채움 (세공고 UI 패턴), 상한 = 다음 1회분 합 |
| FactionsWindow (세력 창) | 세력별 활성 계약 목록: 품목·교환비·N년차/총기간·다음 실행 계절·계약고 충당률 · 해지 버튼 |
| 통합 로그 | 이행/부분 이행/유예/불이행/파기 |
| 경보 (`AlertsPanel`) | 유예 중 계약 ("정기거래 물량 부족 — 2일 내 곡물 16 필요") |

### 상단바는 세공과 달리 요약만

세공 칩은 품목별 `가죽 0/8`까지 펼쳐 보여 주지만, 계약은 여러 건이 쌓이면
그 방식이 피로가 된다. **칩 하나로 합산만** 보여 준다.

```
정기거래 4건 · 다음 6일        ← 평시 (조용한 회색)
정기거래 4건 · 다음 6일 ⚠      ← 다음 실행분이 계약고+재고로 미충당일 때
정기거래 유예 2일 · 곡물 16     ← 유예 중일 때만 구체 품목 노출 (urgent 스타일)
```

- 상태 계산은 `tributeReserveRatio` 패턴의 계약판 (`contractReadinessRatio`) 하나로
- 칩 클릭 → FactionsWindow 열기 (상세는 전부 거기서)
- 활성 계약이 0건이면 칩 자체를 숨긴다

## 9. 구현 순서

| 단계 | 내용 | 검증 |
|---|---|---|
| T1 | `TradeContract` 상태 + 세이브 +1 + 연간 실행기 (이행·유예·불이행·파기) | 장기 시뮬 수년 |
| T2 | 체결 — 협상 accepted에 계약 버튼 + 우호도 기간·상한 검증 | 우호도 구간별 |
| T3 | 계약고 (`tradeContractReserve` + 장터 패널 UI + 실행기 인출 순서) | 격리·반환·상한 |
| T4 | 갱신 모달 + 중도 해지 | 만료 흐름 |
| T5 | 상단바 요약 칩 + FactionsWindow 계약 목록 + 경보 | 육안 |

T1이 코어. T2~T5는 T1 위에 독립적으로 얹힌다. 전부 기존 함수 호출 조합이라
**새 밸런스 축이 없고**, 조기 실장 목표에 맞는 크기다. 계약고(T3)가 빠져도
T1은 일반 재고만으로 동작하므로, 최소 실장은 T1+T2로도 성립한다.

## 10. 열어 둔 판단

- 계약 할인 폭 (0.95) — 스팟 협상이 무의미해지지 않는 선
- 물량 상한 50% — 계약만으로 소금 수요를 다 채울 수 있어야 하는지, 일부는 수동으로 남길지
- 적대 전환 후 우호도 회복 시 정지 계약의 재개 여부
- 하사품 문서의 고유기물(면세 교지 등)과 달리 계약 전용 기물은 두지 않는다 — 1차 범위 밖
- 상단 은 계약에서 은 시세 변동 요소를 넣을지 — 현재 교환가치가 정적이므로 1차는 고정
